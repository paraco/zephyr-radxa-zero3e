## 이 칸이 답한 **포팅의 핵심 질문**

**`ggml-quants.c` 가 Zephyr aarch64 로 고치지 않고 빌드되고 돌아간다.**

계획의 B안(ggml CPU 백엔드 + llama.cpp 의 모델 그래프만)에서 가장 큰 미지수가
"ggml 의 C 가 Zephyr 에서 되는가" 였다. 5천 줄 파일 하나를 `target_sources` 에
그대로 넣어 통과했다. 소스를 한 줄도 고치지 않았다.

필요한 것은 **스텁 네 개**뿐이다 — `ggml_abort` · `ggml_row_size` ·
`ggml_type_name` · `ggml_type_size`. 모두 **양자화** 경로만 쓰는 심볼이고
역양자화는 건드리지 않는다. 그래도 스텁은 불리면 `k_panic()` 한다 —
조용히 틀린 값이 나오는 쪽이 더 위험하다.

그리고 **값이 비트 단위로 같다.** Q4_0 128개 + Q4_K 512개 전부.
즉 `aarch64-zephyr-elf` 와 호스트 clang 이 같은 부동소수 결과를 낸다.

## 골든값이 ggml 의 C 에서 나온다 — 파이썬이 아니다

`gguf-py/gguf/quants.py` 에도 역양자화가 있지만 쓰지 않았다. 허용 오차가
**0** 인데 파이썬과 C 는 연산 결합 순서가 달라 반올림이 달라질 수 있다.
골든값은 **우리가 포팅하는 바로 그 코드**에서 나와야 한다.

`tools/l3_golden.sh` 가 `ggml-quants.c` 한 파일 + 스텁만 호스트에서 묶어
`dequantize_row_q4_0`/`_q4_K` 를 직접 부른다. llama.cpp 전체를 cmake 로
짓지 않는다. 오프셋은 `apps/llm_l2/src/l2_golden.h` 에서 읽어 손으로 적지 않는다.

**f32 를 비트 패턴으로 적는다.** 10진수로는 비트 일치를 확인할 수 없다.

## 함정 넷 — 골든값이 실제로 품고 있는 것

**① 음의 0.** 골든값에 `0x80000000` 이 있다. `y = x0*d` 에서 `x0=0`, `d<0` 인
경우다. `+0.0` 을 내는 구현은 **값으로는 같고 비트로는 다르다.** 비교가
비트 단위라 잡힌다. 10진수 비교였다면 통과했을 것이다.

**② Q4_0 의 니블 배치가 순차가 아니다.**
```c
y[i*qk + j + 0   ] = x0*d;   /* 하위 니블 → 앞 절반 */
y[i*qk + j + qk/2] = x1*d;   /* 상위 니블 → 뒤 절반 */
```
순서대로 쓰면 **형태는 맞고 값이 섞인다** — 계획서가 L5a-5 에서 경고하는
"축을 뒤집어도 형태는 맞아서 조용히 틀린다" 와 같은 종류다.

**③ Q4_K 의 결합 순서.** `d1 = d*sc` 를 먼저 묶고 그 다음 `d1*q - m1` 이다.
`d*(sc*q)` 로 묶으면 반올림이 달라져 비트 일치가 깨진다.

**④ `block_q4_K` 는 공용체(union)다.** `d`/`dmin` 이 `GGML_COMMON_AGGR_S`
익명 구조체 안에 있고 `ggml_half2 dm` 과 겹친다. 크기 144 를 `BUILD` 때
확인한다 — 패딩이 다르면 전부 어긋난다.

## ⚠ 내가 실제로 걸린 오진

처음에 `L_BLOB=` 을 빼먹고 돌렸다. 전부 0 인 메모리를 역양자화하면
Q4_0 은 `-8 × 0 = **-0.0**`, Q4_K 는 `0 × 0 - 0 = **+0.0**` 이 나온다.
**그럴듯한 부동소수 값**이라 "ggml 포팅이 틀렸다" 로 읽혔고, 실제로
`ggml_fp16_t` 가 `__fp16` 으로 잡혀 값 변환이 일어났다는 가설까지 세웠다
(틀린 가설이었다 — `ggml_half` 는 C 경로에서 항상 `uint16_t` 다).

그래서 **양쪽에 자기 진단을 넣었다:**
- `tools/qemu_run.sh` 가 `app.overlay` 에 `model_blob` 이 있고 `L_BLOB` 이
  없으면 **돌리기 전에** 경고한다.
- 앱의 `[0a]` 가 매직을 먼저 보고 원인을 지목한다.
