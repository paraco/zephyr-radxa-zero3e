# L8b — CPU 클럭을 직접 잰다

L8a 의 결론이 **내 사이클 추정에 의존**했으므로, 추정을 빼고 PMU 사이클
카운터(`PMCCNTR_EL0`)와 24 MHz arch 타이머를 같이 읽어 주파수를 직접 잰다.

## ✅ 실기 측정 — 2026-11-07

```
arch 타이머 CNTFRQ = 24000000 Hz
PMU 사이클 카운터 ... OK
    1회차: 사이클 163200241 / 타이머 4800012 tick → **815 MHz**
    2회차: 사이클 163200399 / 타이머 4800012 tick → **815 MHz**
    3회차: 사이클 163200415 / 타이머 4800005 tick → **816 MHz**
간접 측정 (의존 곱 사슬, 반복당 ~4사이클 가정)
    2천만 반복 533 ms → 반복당 26 ns → 4사이클이면 **149 MHz**
메모리 읽기 (모델 창, arch 타이머 41.7 ns 해상도)
    32 KiB (L1)    827 MiB/s  (64 MiB 를 77 ms)
    256 KiB (L2)   729 MiB/s  (64 MiB 를 87 ms)
    4 MiB          708 MiB/s  (64 MiB 를 90 ms)
    32 MiB         706 MiB/s  (64 MiB 를 90 ms)
```

## ① CPU = **815 MHz** (1.8 GHz 의 2.2배 아래)

세 번 재서 815·815·816 MHz 로 일치한다. PMU 가 트랩되지 않았다
(TF-A 가 `MDCR_EL*.TPM` 을 켜 두지 않았다).

RK3566 의 A55 최대는 1.8 GHz 다. U-Boot 가 보수적인 값으로 두고 리눅스
cpufreq 가 올리는 구조이고, Zephyr 에는 이 SoC 용 CPU 클럭 드라이버가 없다.
**815 MHz 는 부트로더가 남겨 둔 값이다.**

## ② 간접 추정이 **5.5배 틀렸다**

같은 칸에서 "반복당 4사이클" 을 가정한 간접 측정은 **149 MHz** 를 냈다.
실제는 815 MHz 이므로 루프가 반복당 **약 21사이클**을 쓴 것이다 —
내 가정이 5배 어긋났다.

⚠ **L8a 의 "120~155 MHz" 는 이 틀린 가정에서 나온 값이다.** PMU 로 재지
않았다면 엉뚱한 곳(전압·PLL)을 팠을 것이다. **가정이 들어간 수치는 가정이
깨질 수 있다는 표시와 함께 써야 한다.**

## ③ L1 이 32 MiB 와 거의 같다 — 캐시가 안 먹는다

```
L1 32 KiB  827 MiB/s   ←→   32 MiB  706 MiB/s    (차이 17%)
```

815 MHz A55 에서 L1 상주 데이터는 **수 GiB/s** 여야 한다. 827 MiB/s 는
8바이트 적재당 **7.9 사이클**이다. 크기를 바꿔도 평평한 것은 **캐시가 안
먹는 메모리**의 특징이다.

⚠ 이 측정은 **모델 창에서만** 했다. sram0 도 같은 방식으로 재야 비교가
성립한다 — `apps/llm_l8c`. L8a 가 32 MiB 한 점으로 "속성 문제 아니다" 로
결론 낸 것이 왜 틀렸는지는 `apps/llm_l8a/README.md` 의 "내가 틀린 곳" 참고.
