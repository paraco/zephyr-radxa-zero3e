# llama.cpp src/ 소스 목록 — **단일 출처**.
#
# cmake/llm_llama.cmake(Zephyr)와 tools/host_golden_llama.sh(호스트)가
# **이 파일 하나**를 읽는다. cmake/ggml-sources.txt 와 같은 이유다 — 목록을
# 두 군데 두었다가 한쪽에만 파일을 더해 "호스트 골든값과 보드 결과가 다른
# 코드에서 나온" 상태가 된 적이 있다.
#
# 경로는 llama.cpp/ 기준.
#
# ⚠ `llama-mmap.cpp` 는 **없다.** 이 툴체인은 _POSIX_MAPPED_FILES 를 정의하지
#   않아 상류가 fallback 로 가고 llama_mmap::SUPPORTED=false 가 된다
#   (llama-mmap.cpp:691). 그러면 로더가 use_mmap 을 끄고 508 MiB 를 또
#   복사한다 — 창 여유 4.15 MiB 에 불가능하다.
#   대신 apps/llm_common/llama_mmap_zephyr.cpp 를 링크한다
#   (docs/l6-decisions.md 결정 3).

# ── L6b — 모델 그래프 전체 ───────────────────────────────────────────────
#
# ⚠ **왜 전부인가.** `llama-model.cpp:351` 의 공장 switch 가
#   `new llama_model_qwen35(params)` 꼴로 **175개 모델 클래스의 생성자를
#   전부 참조**한다. 하나만 쓰더라도 링커는 전부를 요구한다
#   (`-ffunction-sections -Wl,--gc-sections` 는 **참조된** 심볼을 못 버린다).
#
#   176개를 스텁으로 채우는 길도 있었으나, 클래스마다 vtable 과 헤더 정의가
#   얽혀 있어 상류와 어긋날 위험이 크다. OTA 상한에 여유가 7.2 MB 있으므로
#   **먼저 재 본다** — 들어가면 그대로 쓴다.
#
# ⚠ `llama_split_zephyr.cpp` 는 L6b 에서 **쓰지 않는다.** `src/llama.cpp` 가
#   들어오면 `llama_split_path`·`llama_split_prefix` 가 중복 정의된다.
#   `llm_llama.cmake` 가 묶음 이름으로 가린다.
#
# ⚠ `src/llama.cpp` 는 cmake 가 만드는 `llama-version.h` 를 요구한다.
#   `apps/llm_common/llama-version.h` 에 그 자리값을 넣어 두었다.
#
# ⚠ `src/llama-quant.cpp` 는 **없다.** 모델 **양자화기**이고 `std::mutex` ·
#   `std::thread` 를 쓴다 — 이 툴체인의 libstdc++ 에는 둘 다 없다
#   (`_GLIBCXX_HAS_GTHREADS` 미정의, `zephyr_future.h` 머리말 참고).
#   `llama_model_quantize` · `llama_model_quantize_default_params` 는 그 파일
#   안에서만 정의·사용되고 다른 소스가 참조하지 않으므로 **스텁도 필요 없다**.
#   보드에서 모델을 양자화할 일은 없다(쓸 파일 시스템도 없다).
#   ⚠ 혹시 나중에 undefined reference 가 나면 그때 스텁을 만든다 —
#     미리 만들면 "쓰이지 않는 코드" 가 늘기만 한다.
