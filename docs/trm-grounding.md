# 하드웨어 사실의 출처 — TRM 근거 대장

이 저장소의 모든 하드웨어 상수(주소·오프셋·비트·인터럽트 번호·클럭)에는
출처가 있어야 한다. 이 문서는 **그 등급을 정하고, 지금 무엇이 미확인인지,
그리고 TRM 이 애초에 답할 수 없는 영역은 어디인지**를 적는다.

정본 문서: **Rockchip RK3568 TRM Part1 V1.3 / Part2 V1.1**
(RK3566 은 RK3568 과 같은 TRM 을 쓴다. 다이 차이는 주변장치 개수·핀 수다.)
Part1: `rockchip.fr/Rockchip%20RK3568%20TRM%20V1.3%20Part1.pdf` (11.3 MB)
⚠ 전체 파싱은 시간 초과한다 — **장 단위로 접근한다.**
⚠ 내려받기는 사용자 승인을 받는다 (이전 승인은 이어지지 않는다).

---

## 1. 왜 TRM 이 정본이어야 하는가 — 실측된 이유

**Zephyr 인트리 `dts/arm64/rockchip/rk3568.dtsi` 를 신뢰할 수 없다.**
같은 노드 하나(`uart2`)에서 두 값이 의심스럽다:

| 인트리 값 | 우리 값 | 근거 |
|---|---|---|
| `clock-frequency = <12000000>` | **24000000** | 분주비 계산 + 실측. 12 MHz 면 115200 에서 오차 7%, 1500000 에서 50% — 한 바이트도 못 받는다. **실기로 오류 입증** |
| `interrupts = <GIC_SPI 118 IRQ_TYPE_EDGE ...>` | **IRQ_TYPE_LEVEL** (`apps/moru/app.overlay`) | Linux 메인라인 DT. **TRM 미확인** |

⚠ 두 번째 줄에 단서를 하나 달아야 한다 — **TRM 의 인터럽트 요약표가 트리거
타입까지 적는지는 확인하지 않았다.** INTID 와 소스 이름만 적을 수도 있다.
그렇다면 그 사실의 정본은 TRM 이 아니라 해당 주변장치 장의 인터럽트 서술이거나,
없을 경우 Linux DT 가 최상위 출처로 남는다. §5 의 2번 항목은 그 전제까지
포함해 확인한다.

하나가 실측으로 틀렸음이 확인된 파일의 다른 값도 의심해야 한다. 그리고
**트리거 타입은 TRM 인터럽트 표만이 정본**이다 — Linux DT 도 2차 출처다.

지금 폴링 모드(`SHELL_BACKEND_SERIAL_API_POLLING=y`)라 트리거 타입이
무해하지만, 인터럽트 구동으로 바꾸는 순간 정본이 필요해진다.

## 2. 출처 등급

새 하드웨어 상수를 코드에 넣을 때 **등급과 출처를 주석에 쓴다.
등급 없는 상수는 커밋하지 않는다.**

| 등급 | 뜻 | 예 |
|---|---|---|
| **T** | TRM 에서 직접 확인 (절·쪽 기록) | USB2PHY GRF 비트 (Part1 V1.3 3.9절 419쪽) |
| **L** | 이 보드에서 실측 (라이브 DT·sysfs·레지스터 읽기) | DRAM `0x00200000~0x80000000`, dwc3 SPI 169 |
| **D** | Linux 메인라인 디바이스트리 (MIT 선택 가능) | uart2 트리거 타입, 칩 ID 의 OTP 오프셋 |
| **C** | 타 OS 드라이버에서 **사실만** 확인 (코드는 베끼지 않음) | GPIO v2 오프셋 (FreeBSD, BSD-2) · OTP 절차 (Linux, GPL-2.0) |
| **I** | 계산·추론 | uart2 24 MHz (분주비가 정수여야 한다는 제약에서) |
| **G** | 근거 없는 추측 | **코드에 남아 있으면 안 된다** |

`T` 와 `L` 이 어긋나면 **`L` 이 이긴다** (실물이 문서를 이긴다). 어긋난
사실 자체를 기록한다.

## 3. 오늘까지의 실패를 TRM 이 막을 수 있었나 — 건별 판정

**정직한 결론을 먼저 쓴다: 막을 수 있었던 것은 7건 중 1건이다.**
TRM 을 확보하는 것이 bring-up 삽질의 해답이 아니다. 이 착각을 막기 위해
판정을 남긴다.

| 실패 | TRM 판정 | 설명 |
|---|---|---|
| `CONFIG_INIT_STACKS` 로 부팅 불가 (왕복 3회) | **무관** | Zephyr arm64 리셋 경로 문제. TRM 에 Zephyr 는 없다 |
| `IRQ_TYPE_EDGE` 를 원인으로 오판 | **막을 수 있었을 것** | TRM 이 트리거 타입을 적는다면 가설을 바로 버릴 수 있었다. 단 §1 의 단서 — TRM 이 그것을 적는지 자체가 미확인이다 |
| `DW8250` busy-detect 를 원인으로 오판 | **부분** | TRM UART 장이 USR/busy-detect 레지스터 존재를 답한다. 원인은 아니었지만 **빨리 버릴 수 있었다** |
| `moru_stage.c` 의 `device_map()` @ `PRE_KERNEL_1` | **무관** | Zephyr init 순서 |
| LED 스레드 스택 1024 로 크래시 | **무관** | Zephyr 스택 요구량 |
| tio 버퍼링·보율 불일치·`mdir` 미확인 | **무관** | 호스트 도구 |
| 기준선 없이 변경 20개를 쌓음 (왕복 4회) | **무관** | 절차. [bringup-rules.md](bringup-rules.md) 참조 |

즉 **가장 비싼 두 항목(왕복 3회 + 4회)은 TRM 과 무관했다.** 비용을 줄이는
것은 TRM 이 아니라 작업 규율이다.

## 4. 증상을 보고 TRM 을 볼 일인지 즉시 판정하는 표

| TRM 이 정본인 것 | TRM 사정권 밖 (봐도 답이 없다) |
|---|---|
| 레지스터 주소·오프셋·비트 이름·RO/RW | Zephyr Kconfig 의 상호작용·`select` 번짐 |
| 메모리맵·예약 영역 | Zephyr init level 순서, 링커 배치 |
| 인터럽트 번호·**트리거 타입** | U-Boot 가 넘길 때의 MMU·캐시·EL 상태 |
| 클럭 트리·분주·게이트·소프트리셋 | TF-A / BL31 이 실제로 지원하는 PSCI 범위 |
| IO 다중화(iomux)·드라이브 세기 | 호스트 도구 (tio·mtools·picotool·ioreg) |
| 리셋 종류와 절차 (CRU_GLB_SRST) | 보드 배선·헤더 핀 배치 (Radxa 사양서) |
| 전원 도메인·PHY 설정 | SD 카드 굽기 절차, U-Boot 환경변수 |
| hiword-mask 규약 | Zephyr 드라이버 모델·DT 바인딩 |

**판정 규칙:** 증상이 "하드웨어가 이 비트에 어떻게 반응하는가" 면 TRM.
"소프트웨어가 왜 이 순서로 도는가" 면 TRM 이 아니다.

## 5-a. 메모리 아페처 — Part1 Table 1-1 로 확인 (2026-11-07)

**출처:** Rockchip RK3568 TRM Part1 **V1.3-20220930P**, §1.1 "Address Mapping",
Table 1-1 (PDF 10~13쪽). 받은 파일 sha256
`6c14b5844a526f8d29d727ef68353712dd225a94746caab6b0ebddc6df37c8d9` (11,814,295 B).
표에서 195행을 뽑아 기계적으로 대조했다.

### 결과 — **우리 세 창에 겹치는 아페처가 없다**

```
Table 1-1 의 최저 시작 주소 = 0xF0000000  (PCIe3x2_S, 32MB)
  → 0x00000000 ~ 0xF0000000 에는 주변장치 아페처가 **하나도 없다**
    (4 GB 위의 PCIe 창 0x300000000 은 별개)

sram0     0x40000000 .. 0x48000000   겹치는 항목 없음
OTA 적재  0x50000000 .. 0x50040000   겹치는 항목 없음
모델 창   0x58000000 .. 0x78000000   겹치는 항목 없음
```

### ⚠ 이 표가 **말하지 않는 것**

**Table 1-1 에는 DRAM 행이 아예 없다.** 주변장치만 나열한다. 그래서 TRM 이
증명하는 것은 **"그 구간에 주변장치 아페처가 없다"** 이고,
**"그 구간에 DRAM 이 실장돼 있다"** 는 아니다. 후자는 보드·DDR 트레이닝
사실이고 TF-A 가 초기화한 뒤 DT 로 알려 주는 값이다 — **등급 L**:

```
라이브 DT  reg = <0x0 0x00200000 0x0 0x7fe00000>  →  DRAM 0x00200000 .. 0x80000000
```

**두 절반이 함께여야 답이 된다.** 모델 창 `0x58000000~0x78000000` 은
`0x80000000`(실장 끝) 아래이고 `0xF0000000`(최저 아페처) 아래다 → 안전하다.

### 같은 표로 함께 확인한 값들

| 우리 값 | TRM Table 1-1 | 결과 |
|---|---|---|
| `uart2` base `0xfe660000` | `UART2 0xFE660000` 64KB | ✅ 일치 (인트리 dtsi 의 **base 는 맞았다**) |
| `GPIO0` base `0xfdd60000` | `GPIO0 0xFDD60000` 64KB | ✅ 일치 |
| dwc3 base `0xfcc00000` | `USB3_0 0xFCC00000` 4MB | ✅ 일치 |
| `USBPHY_U3_GRF 0xFDCA0000` | 같음 32KB | ✅ 일치 (기존 기록 재확인) |
| `OTP_NS 0xFE38C000` | 같음 16KB | ✅ 일치 (기존 기록 재확인) |

표의 사소한 이상: `GIC600` 이 두 번 나오고(`0xFD400000` 4MB · `0xFDE30000`
0KB) 뒤쪽 크기가 0KB 다. 우리가 쓰는 값과 무관하므로 그대로 적어 둔다.

## 6. 남은 계획(B1~B4)에서 TRM 이 필요한 지점

| 묶음 | TRM 필요 | 비고 |
|---|---|---|
| **B1** Linux 형식 부팅 메시지 | **없음** | 전부 Zephyr 쪽 |
| **B2** `moru info` · `VERSION` · 셸 모듈 | **없음** | hwinfo 는 이미 TRM 근거 확보 |
| **B3** `moru usb` 진단 API | **없음** | dwc3 는 Synopsys/Fuchsia, PHY GRF 는 3.9절 확보 |
| **B4** `moru reboot` | **PSCI 실패 시 필수** | §5 의 1번 항목. `moru reboot probe` 로 PSCI 를 먼저 가린다 |

→ **2026-11-06 갱신: 남은 사유는 §5 의 2·3번뿐이다.** B4 의 CRU 대안은
PSCI 1.1 이 응답하는 것이 실기로 확인돼 우선순위가 내려갔다. 둘(uart2
트리거 타입 · UART USR 레지스터)은 둘 다 인터럽트 구동으로 바꿀 때 필요한
것이고 지금은 폴링 모드라 급하지 않다. 즉 **TRM 을 지금 당장 받을 이유가
없다.**

## 7. 미해결 — `CONFIG_INIT_STACKS` 는 TRM 영역이 아니다

유죄는 입증됐고(실기 3회) **기전은 설명되지 않았다.** 확인된 범위:

- 동기 마커(`uart_poll_out`)조차 안 나오므로 **`PRE_KERNEL_2` 이전**에 죽는다.
  → 스레드 스택 칠하기(`thread.c`)는 범인이 아니다. 스레드 생성 전이다.
- `arch/arm64/core/reset.S:199-215` 가 `__reset_prep_c` **뒤**, MMU·EL 전환
  **앞**에서 `sp` 기준으로 ISR 스택을 0xAA 로 칠한다.
- 그 루프는 이 보드 수치로 정상이다: `ISR_STACK_SIZE=4096` =
  `__z_interrupt_stack_SIZEOF` 0x1000, 시작·끝 차이 0xFF8(8의 배수)이므로
  `beq` 가 정확히 종료하고 영역을 벗어나 쓰지 않는다.
즉 **루프 자체에는 정적 결함이 없다.**

### ✅ 확정 — EL2 데이터 캐시 (실기 2026-11-06)

루프가 아니라 **그 루프가 도는 시점의 캐시 상태**가 문제라는 가설이다.
근거는 셋 다 확인된 사실이다:

| 근거 | 확인 |
|---|---|
| Zephyr 가 **EL2 에서 부팅**한다 | 실측 — U-Boot 가 EL2(SPSR 0x3c9)에서 `go` 한다 (hardware-verified.md:1348) |
| `arch/arm64/core/reset.c:158` 의 dcache clean+disable 블록이 **컴파일되지 않는다** | `CONFIG_ARM64_DCACHE_ALL_OPS` 가 n → 의존하는 `ARM64_BOOT_DISABLE_DCACHE` 는 선택조차 안 된다 (`build/zephyr/.config` 확인) |
| 그 Kconfig 의 help 가 **정확히 이 위험을 기술**한다 | `arch/arm64/core/Kconfig:446` — "To make it safe, **if data cache is enabled in case of Zephyr is booting from EL2**, enable this option, it will clean and invalidate all data cache and then disable data cache" |

기전(가설): U-Boot `go` 는 `booti` 와 달리 캐시를 정리하지 않으므로 EL2 의
MMU·dcache 가 켜진 채 진입한다 → `reset.S:199-215` 의 0xAA 칠하기가 ISR 스택
4 KiB(64바이트 줄 64개)를 **dcache 에 dirty 로** 남긴다 → `switch_el` 로 EL1 에
내려가면 EL1 SCTLR 이 초기값이라 MMU·C 가 꺼져 이후 스택 접근은 캐시를
우회해 DRAM 으로 간다 → 나중에 그 dirty 줄이 evict 되며 **EL1 이 DRAM 에 써
둔 값을 0xAA 로 덮는다** → 복귀 주소나 지역 변수 손상 → `PRE_KERNEL_1` 전에
무음으로 죽는다.

`INIT_STACKS=n` 이면 EL2 구간에서 더럽혀지는 것이 함수 프레임 몇백 바이트뿐
이고 그 영역은 EL1 이 곧 다시 쓰므로 증상이 드러나지 않는다 — **4 KiB 를
칠할 때만 "EL1 이 아직 쓰지 않은 깊은 영역"에 stale dirty 줄이 남는다.**
이것이 "루프는 정상인데 켜면 죽는" 모순을 설명한다.

**실기로 확정됐다 (2026-11-06).** `INIT_STACKS` 를 양쪽 다 `y` 로 두고 캐시
두 설정만 토글해 두 방향을 재현했다 — `464a4ce`(캐시 없음) 무음 ❌,
`ef6780f`(캐시 있음) 부팅 ✅. `kernel thread list`·`stacks` 가 동작하고,
후자가 `IRQ 00`(ISR 스택) usage 500/4096 을 보여준다 — 0xAA 칠하기가 정상
작동한다는 직접 증거다.

**진짜 원인은 `INIT_STACKS` 가 아니었다.** 그것은 증상을 드러내는 방아쇠였고,
원인은 EL2 부팅 시 dcache 미정리다. 유죄로 판정했던 설정이 실은 무죄였던
셈이다 — "유죄 입증"과 "기전 설명"을 구분해 적어 둔 것이 이 수정을 가능하게
했다 ([bringup-rules.md](bringup-rules.md) 규칙 4).

### 다음 실험 — TRM 이 아니라 이 순서

| | 실험 | 비용 | 가리는 것 |
|---|---|---|---|
| **1** | 캐시 두 설정 + `CONFIG_INIT_STACKS=y` | 실기 1회 | **✅ 완료 — 부팅. 기전 확정, 두 명령 복구** |
| **2** | **`FRAME_POINTER`·`EXCEPTION_STACK_TRACE` 재시험** | 실기 1회 | 같은 증상(무음)으로 포기했던 설정이다. 같은 원인일 가능성이 있다 — 맞으면 **역추적을 되찾아** 남은 작업의 디버깅 비용이 전부 내려간다. 전제조건으로 `SHELL_STACK_SIZE=4096` 을 먼저 넣었다(아래) |
| 3 | 다른 arm64 보드(QEMU)에서 캐시 설정 없이 `INIT_STACKS=y` | **실기 0회** | Zephyr 일반 문제인지 확인. 상류 보고의 근거가 된다 |
| ~~4~~ | ~~`reset.S` 루프 삭제~~ | — | 불필요해졌다 |

**Zephyr 상류에 보고할 거리.** "루프 결함" 이 아니라 **"EL2 에서 부팅하는
보드에서 `ARM64_BOOT_DISABLE_DCACHE` 가 기본으로 꺼져 있고, 의존하는
`ARM64_DCACHE_ALL_OPS` 도 꺼져 있어 선택지 자체가 보이지 않는다. 그 결과
`INIT_STACKS` 같은 평범한 설정 하나로 콘솔 출력 한 글자 없이 죽는다"** 다.
최소한 그 Kconfig 의 help 를 증상과 함께 적거나, EL2 부팅 감지 시 기본값을
켜는 쪽이 맞다. 실험 3으로 일반 문제임을 확인한 뒤 보고한다.

### 되찾은 명령이 바로 값을 냈다

`kernel thread stacks` 첫 출력에서 `shell_uart` 가 **2196/3072 (71 %)** 였다.
다른 스레드는 모두 4096 인데 그것만 arm64 기본 3072 였고 여유가 876 바이트다.
`CONFIG_SHELL_STACK_SIZE=4096` 으로 올렸다 — **추측이 아니라 실측으로**
결정한 첫 사례다. `FRAME_POINTER` 재시험의 전제조건이기도 하다(프레임
포인터는 스택을 더 쓰므로, 71 % 에서 시험하면 "기동 실패"와 "셸 스택 넘침"을
가릴 수 없다).

**초기 단계 출력 수단의 제약** (실험을 설계할 때): `reset.S` 구간은 UART 로
찍을 수 없다. Zephyr 가 115200 으로 재설정하기 전이라 U-Boot 의 1.5 Mbps 로
나가고, 쓰는 CP2102 는 1 Mbps 한계다. 그 구간을 보려면 GPIO raw MMIO 를
쓴다 (MMU 가 꺼진 상태에서도 물리 주소 직접 쓰기는 된다).

TRM 이 간접적으로 관련될 수 있는 유일한 지점은 §5 의 7번(DRAM 하단 예약
영역)이다. 그것이 `z_interrupt_stacks` 와 겹칠 가능성은 낮지만 — 이미지는
`0x40000000` 에 있고 예약 영역은 `0x00200000` 아래다 — 메모리맵으로
교차 확인할 가치는 있다.
