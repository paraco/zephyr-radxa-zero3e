# L8 — 왜 23.6초/토큰인가 (원인 규명 완료)

L6c 가 실기에서 **토큰당 23.6초**(0.042 tok/s)를 냈다. A55 한 코어로
0.8B Q4 는 보통 1~4 tok/s 이므로 **25~100배** 느렸다. 성능 플래그를 뒤집기
전에 원인을 재는 것이 L8a~L8d 였다.

## 셈이 맞는다

| 원인 | 배수 | 근거 | 우리가 고칠 수 있나 |
|---|---|---|---|
| CPU **815 MHz** (최대 1.8 GHz) | **2.2×** | PMU 사이클 카운터, 3회 일치 (L8b) | ❌ CRU+PMIC — U-Boot/TF-A 영역 |
| **`SMPEN=0`** → 내부 공유 캐시 무력 | **~5~10×** | `CPUECTLR_EL1`=0x0020000000040000 · 대역이 크기와 무관하게 평평 (L8c·L8d) | ❌ **EL3 가 쓰기를 막는다** |
| **한 코어** (4개 중 1) | **≤4×** | `CONFIG_MP_MAX_NUM_CPUS 1` | ✅ Zephyr SMP + PSCI CPU_ON |
| repack 없음 · `-ffp-contract=off` | 작다 | 모델이 거의 Q4_K 라 repack 효과는 미지 | ✅ |

**2.2 × 5~10 × 4 ≈ 44~88배.** 설명해야 했던 25~100배와 맞는다.

## 확정된 사실

```
CLIDR_EL1 0x82000023   L1 I+D 분리 · D 32 KiB · L2 통합 512 KiB
SCTLR_EL1 0x30d0180d   M=1 C=1 I=1        — 캐시는 켜져 있다
MAIR/페이지표           AttrIndx=4 → 0xff = Normal WB RW-alloc · SH=3
CPUECTLR_EL1           0x0020000000040000 → **SMPEN(bit 6) = 0**
CPU 주파수              **815 MHz** (PMU, 3회)
읽기 대역 (크기 무관)   L1 837 · L2 730 · DRAM 707 MiB/s
부팅 진입 EL            **EL2**
EL2 에서 CPUECTLR       읽기 ✅ / 쓰기 ❌ (트랩 → 리셋)
```

Cortex-A55 에서 `SMPEN=0` 이면 **내부 공유 캐시 가능 메모리가 사실상
비캐시로 동작한다.** 페이지가 캐시 가능이라고 말하는데도 L1·L2·DRAM 대역이
평평했던 것이 그 증상이다.

## 왜 우리가 고칠 수 없나

`CPUECTLR_EL1` 쓰기는 EL3 가 `ACTLR_EL3.CPUECTLR`(bit 1)로 허락해야 한다.
**TF-A(BL31)가 허락하지 않았다.** 증거:

- EL2 훅에서 **읽기**는 된다 (`[0]` 흔적이 값을 가져왔다)
- 같은 자리에서 **쓰기**를 하면 보드가 한 글자도 못 찍고 리셋된다
- 캐시가 켜진 뒤 런타임에 쓰면 `esr 0x8a000000` (EC 0x22) 예외
  — ARM 이 "캐시·MMU 를 켠 뒤의 SMPEN 변경은 미정의" 라고 적은 그대로다

즉 **SMPEN 과 CPU 클럭은 둘 다 U-Boot/TF-A 가 정하고, Zephyr 에서 되돌릴
수 없다.** 이 이미지로 베어메탈·RTOS 를 돌리면 **SoC 능력의 1/10 수준**으로
동작한다.

⚠ 이것은 이 보드의 **부트 펌웨어**에 대한 발견이다. Radxa 의 U-Boot 는
리눅스가 cpufreq·coherency 를 맡는다고 보고 넘긴다. 리눅스는 둘 다 켠다.

## 그래서 할 수 있는 것

| | 무엇 | 얻는 것 | 비용 |
|---|---|---|---|
| **A** | Zephyr SMP + PSCI CPU_ON 으로 **4코어** | ≤4× → **6초/토큰** | Zephyr 작업. PSCI 는 `moru reboot probe` 로 BL31 응답을 먼저 가린다 |
| **B** | repack · `-ffp-contract=fast` · `-O3` | 미지, 아마 1.2~2× | 골든값 재생성 필요(결정 1 의 전제가 바뀐다) |
| **C** | U-Boot/TF-A 를 다시 빌드해 SMPEN·클럭 설정 | **~10×** | 보드 부트 체인 교체. 되돌리기 어렵다 |
| **D** | 지금을 받아들이고 **더 작은 모델** | — | 0.8B 가 23.6초면 0.1B 급은 3초대 |

**A 가 먼저다** — Zephyr 안에서 되고, 4배는 확실하고, 되돌리기 쉽다.
C 는 가장 크지만 보드의 부트 체인을 바꾸는 일이라 **사용자 결정이 필요하다**.

## 측정에서 내가 틀린 것들 (기록)

이 칸들에서 네 번 틀렸고 전부 측정으로 바로잡았다. 남겨 두는 이유는 같은
함정을 다시 밟지 않기 위해서다.

| 틀린 것 | 어떻게 드러났나 |
|---|---|
| "모델 창이 캐시 안 됨" (32 MiB 한 점 비교) | **한 점으로는 두 가설을 못 가른다** — 32 MiB 는 L2 를 넘어 캐시와 무관하게 DRAM 대역에 묶인다. 크기 쓸기 + 페이지 표 직독으로 가렸다 |
| CPU "120~155 MHz" (반복당 4사이클 가정) | PMU 로 직접 재니 **815 MHz**. 가정이 5.5배 틀렸다 (실제 ~21사이클) |
| 진입 EL 이 EL1 | `moru info` 의 "EL1" 은 Zephyr 가 **내려온 뒤**의 CurrentEL. 실제는 **EL2** |
| 세 훅에 쓰기를 넣어도 된다 | 콘솔 초기화 **전**이라 죽으면 진단 불가능. 읽기만 하는 판으로 바꿔 어느 EL 인지 먼저 가렸다 |

**공통점:** 측정이 가설을 **구분할 수 있는지** 먼저 따지지 않았다.
`docs/bringup-rules.md` 규칙 7("출력을 못 읽는 곳에는 입증된 문법만")과
같은 결의 교훈이다.

## 2026-11-07 저녁 — SMP 는 이 보드에서 **부팅을 막는다** (실기 확인)

### 무엇을 재려 했나

주 코어의 `SMPEN=0` 은 L8d 가 확인했다. 가설: **PSCI `CPU_ON` 으로 보조
코어를 올리면 BL31 이 그 코어의 리셋 경로를 돌면서 SMPEN 을 켜 줄 수 있다.**
맞다면 멀티코어가 4배가 아니라 20~40배가 되고 펌웨어 재빌드가 불필요하다.

### 결과 — 침묵. 그리고 대조군으로 원인을 좁혔다

| 이미지 | 설정 | 115200 출력 |
|---|---|---|
| `llm_l8e` | `SMP=y` · `MP_MAX_NUM_CPUS=4` · `PM_CPU_OPS_PSCI=y` | **없음** |
| `llm_l8f` | `SMP=y` · `MP_MAX_NUM_CPUS=1` · `PM_CPU_OPS_PSCI=y` | **없음** |
| `llm_l8d` (대조군) | SMP 없음 | **전체 출력** ✅ |

세 번 모두 **같은 카드·같은 `boot.scr`·같은 CP2102 직결**이다. 대조군이
카드의 `zephyr.bin` 경로로 측정 전체를 찍었으므로 **카드·U-Boot·콘솔은
무죄다.**

`MP_MAX_NUM_CPUS=1` 이면 `z_smp_init` 의 루프가 0회라 **`CPU_ON` 을 한 번도
부르지 않는다.** 그런데도 침묵했다. 따라서:

> 범인은 `CPU_ON` 이 **아니다.** `CONFIG_SMP` 골격 자체이거나,
> `PM_CPU_OPS_PSCI` 의 `psci_init`(`PRE_KERNEL_1` — 콘솔보다 먼저
> `PSCI_VERSION` SMC)이다.

⚠ 아직 그 둘을 가리지 않았다. `moru reboot probe` 가 런타임에
`PSCI 1.1 (raw 0x00010001)` 을 받았다는 사실은 **`psci_init` 의 무죄를
증명하지 않는다** — 셸에서 쏜 SMC 와 `PRE_KERNEL_1` 의 SMC 는 시점이 다르다.

### 이 목표에 주는 뜻

멀티코어는 **빠른 승리가 아니다.** 그리고 L8 의 두 큰 인자는 SMP 를
필요로 하지 않는다:

| 인자 | 배수 | SMP 필요? |
|---|---|---|
| 클럭 815 MHz → 1.8 GHz | 2.2× | 아니다 |
| SMPEN 0 → 1 (캐시가 먹는다) | 5~10× | 아니다 |
| 코어 1 → 4 | 4× | **그렇다** |

따라서 **클럭과 SMPEN 을 먼저 노린다.** 그 둘만으로 11~22× 이고, SMP 는
그 뒤에 따로 다룬다.

### 측정값 (대조군 L8d4, 재확인)

```
CLIDR_EL1 0x0000000082000023  (LoUIS=0 LoC=2)
  L1 D: 64 B × 4 way × 128 set = 32 KiB
  L2  : 64 B × 16 way × 512 set = 512 KiB
CPUECTLR_EL1 = 0x0020000000040000   SMPEN=0
읽기 대역: 32 KiB 830 · 256 KiB 730 · 32 MiB 708 MiB/s
```

⚠ **32 KiB(L1)와 32 MiB(DRAM)가 830 대 708 MiB/s — 1.17배밖에 차이가
없다.** L1 캐시가 사실상 먹지 않는다는 직접 증거다. SMPEN=0 이면
inner-shareable 캐시 가능 메모리가 비캐시처럼 동작한다는 ARM 의 서술과
맞는다.

# ⚠⚠ 정정 (2026-11-07 밤) — 이 문서의 SMPEN 서술은 **전부 틀렸다**

위쪽 본문과 충돌하면 **이 절이 우선한다.**

## 무엇이 틀렸나 — 레지스터를 잘못 읽었다

ARM 자신의 TF-A 헤더(출처:
`https://raw.githubusercontent.com/ARM-software/arm-trusted-firmware/master/include/lib/cpus/aarch64/cortex_a55.h`,
2026-11-07 원문 확인):

```c
#define CORTEX_A55_CPUECTLR_EL1   S3_0_C15_C1_4      /* ← 진짜 CPUECTLR */
#define CORTEX_A55_CPUECTLR_EL1_L1WSCTL  (ULL(3) << 25)   /* 유일하게 정의된 필드 */

#define CORTEX_A55_CPUACTLR_EL1   S3_0_C15_C1_0      /* ← 우리가 읽던 것 */
#define CORTEX_A55_CPUACTLR_EL1_DISABLE_WRITE_STREAMING  (ULL(1) << 24)
#define CORTEX_A55_CPUACTLR_EL1_DISABLE_DUAL_ISSUE       (ULL(1) << 31)
#define CORTEX_A55_CPUACTLR_EL1_DISABLE_L1_PAGEWALKS     (ULL(1) << 49)
```

`apps/llm_l8d/src/main.c:53,57,62`·`apps/llm_l8e`·`apps/llm_l8f`·`soc_init/smpen.S`
가 모두 **`S3_0_C15_C1_0`** 을 쓴다. 그것은 **`CPUACTLR_EL1`** 이다.

그리고 **A55 의 `CPUECTLR_EL1` 에는 SMPEN 비트가 없다.** A55 는 DynamIQ(DSU)
기반이라 코히런시를 DSU 가 관리한다. SMPEN(bit 6)은 Cortex-A53/A57/A72 의
`CPUECTLR_EL1` 필드다. A55 에 그 비트를 찾으러 간 것 자체가 잘못이었다.

(교차 확인: 메인라인 TF-A 의 `lib/cpus/aarch64/cortex_a55.S` 는 SMPEN 을
세우지 않는다. `CPUECTLR` 참조는 erratum 778703 의 `L1WSCTL` 한 곳뿐이다.
그런데도 Linux 는 이 SoC 에서 정상 부팅한다. "A55 에서 SMPEN 이 코히런시에
필수" 라는 전제가 애초에 성립하지 않는다.)

## 무너지는 결론들

| 주장 | 상태 |
|---|---|
| "주 코어 SMPEN=0" | **무효.** `CPUACTLR_EL1` 의 bit 6 을 읽었다. 그 비트는 ARM 이 공개 정의한 바 없다 |
| "SMPEN 0→1 이면 5~10×" | **무효.** 근거가 없다 |
| "L1≈DRAM(830 vs 708)이 SMPEN=0 의 직접 증거" | **무효.** 아래 참조 |
| "2.2× × 5~10× × 4× ≈ 44~88× 로 셈이 맞는다" | **무효.** 가운데 인자가 사라졌다 |
| 부팅 훅에서 쓰다가 보드가 죽은 일 | 설명이 바뀐다 — `CPUACTLR_EL1` 의 **정의되지 않은 비트에 쓴 것**이다. 죽는 게 당연하다 |
| 런타임 쓰기 트랩(`esr 0x8a000000`, EC 0x22) | `CPUECTLR` 가 아니라 `CPUACTLR` 에 대한 트랩이었다 |

## 대역폭 측정 자체가 의심스럽다

815 MHz 에서 L1 읽기 **830 MiB/s = 사이클당 약 1 바이트**다. A55 의 L1 히트로는
터무니없이 낮다(A55 는 L1 에서 사이클당 16 바이트 급이어야 한다). 즉 이 숫자는
캐시 상태가 아니라 **측정 루프 자체**를 재고 있을 가능성이 크다 — 바이트 단위
로드, 의존성 체인, 언롤 없음.

따라서 "L1 과 DRAM 이 1.17배뿐이니 캐시가 안 먹는다" 는 **측정이 그렇게 말할 자격이
없다.** 캐시가 켜졌는지는 `SCTLR_EL1`.C/M/I 와 PTE 속성으로 직접 확인해야 한다.

## 살아남는 사실

1. **클럭 815 MHz 는 실측이고, 이제 원인이 밝혀졌다.** 업스트림 U-Boot 가
   `APLL_HZ = 816 MHz` 로 **의도적으로** 둔다 —
   `arch/arm/include/asm/arch-rockchip/cru_rk3568.h` 의 `APLL_HZ`,
   `drivers/clk/rockchip/clk_rk3568.c` 의 `rk3568_clk_init()` 이 armclk 가
   `APLL_HZ` 와 다르면 `rk3568_armclk_set_clk(priv, APLL_HZ)` 를 부른다.
   데이터시트 최대는 1.8 GHz → **2.2× 가 실재하고 손이 닿는다.**
2. **전압을 같이 올려야 한다.** Linux OPP(`rk3568.dtsi`):
   408/600/816 MHz = 850 mV · 1104 = 900 · 1416 = 1025 · 1608 = 1100 ·
   1800 = 1150 mV. Zero 3E 의 CPU 전원은 별도 레귤레이터 `vdd_cpu`
   (compatible `rockchip,rk8600`, i2c0 주소 0x40) 다
   (`rk3566-radxa-zero-3.dtsi`). 주파수만 올리면 불안정하다.
3. **SMP 선례가 있다.** Zephyr 에 `roc_rk3568_pc//smp` 와 `rock_3b//smp` 가
   있고, 문서에 보조 코어 1~3 이 올라와 `thread_b` 가 cpu 1 에서 도는 출력이
   있다. 같은 A55·GICv3·PSCI 0.2 구성이다. 그 defconfig 는 우리 보드
   defconfig 와 `SMP`/`MP_MAX_NUM_CPUS`/`PM_CPU_OPS*` 말고는 같다
   (`ARMV8_A_NS=y`·`CACHE_MANAGEMENT=y`·`ARM_ARCH_TIMER=y`·
   `TICKLESS_KERNEL=y`·`CLOCK_CONTROL=y` 전부 우리도 켜 있다).
   ⚠ 한 가지 다르다 — 그 보드는 U-Boot 에서
   **`dcache flush; icache flush; dcache off; icache off; go 0x40000000`**
   으로 띄운다. 우리 `boot.cmd` 는 캐시를 끄지 않고 `go` 한다.

## PSCI 판정의 한계 (스스로 깎는다)

QEMU 에서 `SMP=y`+PSCI 는 죽고 `SMP=y`+PSCI 없음은 떴다. 그런데 그 **QEMU
빌드에는 `CONFIG_ARMV8_A_NS` 가 없었고**(`# CONFIG_ARMV8_A_NS is not set`)
실기 빌드에는 **있다**(`CONFIG_ARMV8_A_NS=y`, 보드 defconfig). 보안 상태가
다르면 SMC 가 BL31 에 닿는 경로가 달라진다. 따라서 **그 QEMU 결과를 실기로
그대로 옮길 수 없다.**

실기 증거는 여전히 두 변수가 섞여 있다:
`{SMP+PSCI 죽음}` 대 `{SMP 없음+PSCI 없음 정상}`.

→ 다음 QEMU 시험은 **`ARMV8_A_NS=y` 를 맞춰서** 돌린다.

## 다음 순서

1. QEMU 에 `ARMV8_A_NS=y` 를 맞추고 PSCI 유무를 다시 가린다 (왕복 0회)
2. 레지스터를 **제대로** 읽는 판을 만든다 — 진짜 `CPUECTLR_EL1`(S3_0_C15_C1_4),
   `SCTLR_EL1`(C/M/I), `CTR_EL0`, 그리고 **제대로 된 대역폭 루프**
   (64비트 로드·독립 스트림 여러 개·언롤). 지금 숫자는 신뢰할 수 없다
3. 그 결과를 보고 클럭(2.2×)으로 갈지 결정한다. 클럭은 전압과 함께다

## 2026-11-07 밤 — L8g 실기 결과: **캐시는 켜져 있는데 먹지 않는다**

같은 코드가 QEMU 에서 10~12 B/cyc, 실기에서 0.65~0.83 B/cyc 다.

```
CNTFRQ 24000000 Hz · CPU 815 MHz
SCTLR_EL1 0x0000000030d0180d   M=1  C=1  I=1
CTR_EL0   0x84448004           DminLine 64 B · IminLine 64 B
CLIDR_EL1 0x0000000082000023 · MIDR 0x412fd050 · CurrentEL 1

CPUECTLR_EL1 (S3_0_C15_C1_4) 0x000000002808bc00   L1WSCTL=0
CPUACTLR_EL1 (S3_0_C15_C1_0) 0x0020000000040000   ← 전 판이 오인한 그 값

읽기 대역 (사이클당 바이트)
   16 KiB  0.83    (L1 32 KiB 안에 들어간다)
   32 KiB  0.75
  128 KiB  0.66
  256 KiB  0.66    (L2 512 KiB 안)
    1 MiB  0.65
    8 MiB  0.65
   32 MiB  0.65    (DRAM)
```

### 읽는 법

**16 KiB 와 32 MiB 가 0.83 대 0.65 — 사실상 같다.** 16 KiB 는 L1(32 KiB)에
완전히 들어가므로 L1 히트만 나야 하고, A55 라면 8~16 B/cyc 이어야 한다.
실제는 **0.83 B/cyc** — 64바이트 캐시 줄 하나에 약 77 사이클이다. 캐시
계층이 **전혀 작동하지 않는다.**

전 판의 830 MiB/s 와 수치가 비슷해 보이지만 의미가 다르다. 전에는 루프가
병목이라 이 결론을 내릴 수 없었다. 지금 루프는 QEMU 에서 10~12 B/cyc 를 내므로
**루프는 무죄**다. 따라서 이번에는 결론을 낼 자격이 있다.

### 무엇이 남았나

`SCTLR_EL1.C=1` 이므로 **"D캐시가 꺼졌다" 는 아니다.** 켜져 있는데 효과가
없다. 남은 후보:

1. **PTE 메모리 속성** — 이 영역이 Normal WB 가 아니라 Device 또는
   Normal-NonCacheable 로 매핑됐다. L8c 의 페이지 워크는 `AttrIndx`→MAIR
   `0xff`(Normal WB)라고 했지만, **그 워크가 이 버퍼의 VA 를 본 것인지
   확인되지 않았다.** 이번에는 **malloc 이 준 정확한 주소**를 걸어 본다.
2. **공유도(SH)** — Inner-Shareable 로 매핑됐는데 코어가 코히런시 도메인에
   참여하지 않으면 캐시 가능 접근이 비캐시로 격하될 수 있다.
3. **CPU 가 전역적으로 느리다** — 메모리와 무관하게 느릴 수 있다. 이것을
   배제하지 않았다. **메모리를 전혀 건드리지 않는 ALU 루프의 IPC** 를 재면
   갈린다. 1~2 IPC 가 나오면 문제는 메모리 하위 시스템이고, ALU 도 느리면
   원인이 다른 데 있다 (PMCCNTR 는 CNTVCT 와 교차 검증됐으니 계수 오류는
   아니다).

⚠ 3번을 먼저 가린다. 2번·1번보다 싸고, 틀린 쪽을 파는 것을 막는다.

## 2026-11-07 밤 — L8h: **메모리는 무죄다. CPU 가 느리다**

```
[3] ALU 루프 — 메모리 접근 0, 독립 add 8 + subs + cbnz = 명령 10개

[1][2] 측정 버퍼의 **정확한 VA** 의 PTE
    malloc → 0x00000000400b3450

    L1[1]=0x0000000040014003 · L2[0]=0x0000000040015003
    L3[179]=0x00600000400b3733

    버퍼 끝(+31 MiB, L2[15] 2 MiB 블록)도 **동일**

    16 KiB 쓰기 1.60 · 32 MiB 쓰기 1.03
```

### 결론 — 앞선 틀을 다시 버린다

**"캐시가 켜졌는데 안 먹는다" 는 틀린 틀이었다.**

1. PTE 속성이 **완벽하다** — `0xff`(Normal WB R/W-alloc), `SH=3`, `AF=1`.
   버퍼의 시작(L3 페이지)과 끝(L2 2 MiB 블록) 둘 다 같다. 매핑 문제가 아니다.
2. **메모리를 한 번도 건드리지 않는 ALU 루프가 IPC 0.45 다.** 메모리
   하위 시스템으로는 이것을 설명할 수 없다.

즉 대역폭이 0.8 B/cyc 인 것은 캐시 때문이 아니라 **CPU 가 명령을 그
속도로밖에 돌리지 못하기** 때문이다. 캐시 계층 이야기는 전부 접는다.

⚠ 이로써 이 문서에서 두 번째로 틀을 버린다. 기록으로 남긴다 —
  (1) "SMPEN=0 이라 캐시가 안 먹는다" → 레지스터를 잘못 읽었다
  (2) "캐시가 켜졌는데 안 먹는다"      → 측정이 CPU 전체 속도를 보고 있었다

### 다음 가설 — 비용이 **명령당**이 아니라 **분기당**인가

한 바퀴 21.96 사이클 / 명령 10개. 그 10개 중 하나가 `cbnz` 다. A55 의
분기 예측 실패 비용이 **10~15 사이클**이다. 즉 매 바퀴 분기를 놓치고 있으면
이 숫자가 거의 그대로 나온다.

**가리는 법: 루프 본체를 언롤한다.**

| 언롤 | 분기당 명령 | 분기당 비용이면 | 명령당 비용이면 |
|---|---|---|---|
| 1× | 10 | 한 바퀴 ≈ 22 사이클 | 한 바퀴 ≈ 22 |
| 2× | 20 | 한 바퀴 ≈ **22** (그대로) | 한 바퀴 ≈ **44** |
| 8× | 80 | 한 바퀴 ≈ **22** (그대로) | 한 바퀴 ≈ **176** |

→ 사이클/명령이 언롤에 따라 **떨어지면** 비용은 분기당이다(예측기·인출).
→ **그대로면** 비용은 명령당이다(실행 자체가 느리다).

동시에 **코드 주소의 PTE** 도 본다. 지금까지 데이터 버퍼만 워크했다. 명령
인출이 비캐시 영역에서 일어나면 그것도 이 모양을 만든다.

# ✅✅ 2026-11-07 밤 — 근본 원인 확정: **DesignWare busy-detect 인터럽트**

L8j 실기 결과. 모든 대조가 설계대로 나왔다.

```
[0] uart2 @ 0xfe660000 (phys) → 0xfe660000 (virt) · Zephyr IRQ 150

[1] 기준선 (레지스터 미접촉)   21.96 사이클/바퀴 · IPC 0.45 · EXC_TAKEN 21,971
[2] 레지스터
      IER 0x00   (ERBFI=0 ETBEI=0 ELSI=0 EDSSI=0)   ← **전부 마스크돼 있다**
      IIR 0xc7   → bits[3:0] = 0x7 = **BUSY DETECT**
      LCR 0x03 · MCR 0x0b · LSR 0x00 · MSR 0x00
[3] IIR 읽은 뒤                21.96 사이클 · EXC 21,970   ← **안 지워진다**
[4] USR 0x03 (BUSY=1 TFNF=1)
    USR 읽은 뒤                 5.00 사이클 · IPC 1.99 · EXC 0   ← **고쳐졌다**
      IIR 0xc1 → 대기 인터럽트 없음
[5] irq_disable                 5.00 (이미 고쳐짐 — 양성 대조)
[6] irq_enable                  5.00 ← 다시 켜도 안 돌아온다 = **영구**
```

## 결정적 증거: `IER = 0x00` 인데도 IRQ 가 걸린다

드라이버가 UART 인터럽트를 **전부 마스크해 두었다.** 그런데도 폭주한다.
**DW_APB_UART 의 busy-detect 는 `IER` 로 마스크할 수 없다.** 이 하나가
다른 모든 가설(ISR 이 LSR 을 안 지운다 / U-Boot 가 IER 를 켜 둔다 /
DTS 의 IRQ_TYPE_EDGE)을 배제한다. IER 가 0 이면 그 어느 것도 IRQ 를
만들 수 없다.

`USR = 0x03` 에 `BUSY=1` — UART 가 자기를 전송 중이라고 보고한다. 조건은
**전송 중에 LCR 을 쓰는 것**이고, U-Boot 가 1.5 Mbps 로 쓰던 UART 를
Zephyr 가 115200 으로 다시 설정하는 그 순간이다. `LCR 0x03` 은 8N1 로
Zephyr 가 쓴 값이다.

## 왜 고침이 영구인가

busy-detect 는 **LCR 쓰기마다 새로 걸린다.** Zephyr 는 init 에서 한 번만
LCR 을 쓰므로, 그 뒤 USR 을 한 번 읽으면 다시 걸릴 일이 없다. `[6]` 에서
`irq_enable` 뒤에도 5.00 을 유지하는 것이 그 증거다.

⚠ 단 **보율을 바꾸면 다시 걸린다.** moru 셸에서 `uart_configure` 를 부르는
  경로가 생기면 그때 또 USR 을 읽어야 한다. 그래서 고침을 init 한 번이 아니라
  **ISR 에서 처리**하는 쪽이 옳다 (Linux 가 그렇게 한다).

## 고침

Linux 는 전용 드라이버로 처리한다 — `drivers/tty/serial/8250/8250_dw.c` 의
`dw8250_handle_irq()` 가 `(iir & 0x3f) == UART_IIR_BUSY` 일 때 USR 을 읽는다.

**Zephyr 의 범용 `uart_ns16550.c` 에는 그 처리가 없다.** 그런데
`dts/arm64/rockchip/rk3568.dtsi` 가
`compatible = "rockchip,rk3568-uart", "ns16550"` 로 선언해 그 드라이버에
바인딩된다. 즉 **메인라인 Zephyr 에서 이 SoC 의 UART 를 인터럽트 구동으로
쓰면 누구나 이 손해를 본다.** 업스트림 보고 거리다.

우리 저장소의 고침은 `soc_init/` 에 넣는다 — 모듈 수준이라 moru 와 앞으로의
앱 전부에 걸린다. 업스트림 ns16550 을 수정하지 않는다(지금까지 업스트림
편집 0줄을 유지해 왔다).

# 2026-11-07 밤 — L8m: **매핑은 무죄. 또 내 루프였다**

```
[3] ALU IPC 1.99                      ← 양성 대조 통과 (폭주 없음)

[1] 힙    AttrIndx=4 → MAIR 0xff · SH=3 · AF=1   (L3 페이지)
    블롭  AttrIndx=4 → MAIR 0xff · SH=3 · AF=1   (L2 2 MiB 블록)
    블롭+256 MiB 도 동일
    → **두 영역의 속성이 완전히 같다**

[2]  4 KiB  힙 3.50 · 블롭 3.50
    16 KiB  힙 3.45 · 블롭 3.53
    32 KiB  힙 2.80 · 블롭 2.97
   256 KiB  힙 3.42 · 블롭 3.31
    32 MiB  힙 3.34 · 블롭 3.23
```

## 판정 — 캐시 문제가 아니다

**4 KiB 와 32 MiB 가 같다.** 4 KiB 는 L1(32 KiB)에 여유롭게 들어가고
32 MiB 는 DRAM 이다. 캐시가 꺼져 있다면 32 MiB 가 훨씬 느려야 한다.
**같다는 것은 둘 다 루프가 병목이라는 뜻이다.**

즉 이 루프로는 **캐시 거동을 볼 수 없다.** "L1 이 안 먹는다" 는 하드웨어의
성질이 아니라 내 측정의 한계였다.

## 범인 — `volatile`

```c
const volatile uint64_t *p = ...;
```

컴파일러가 로드를 지우지 못하게 `volatile` 을 붙였는데, 그것이 로드를
**순서대로 직렬화**한다. 독립 누산기 8개를 둔 의미가 사라진다.
3.50 B/cyc = 64바이트에 18.3 사이클 = 로드당 2.3 사이클인데, A55 의 L1 은
사이클당 1 로드여야 한다.

**이 계열에서 세 번째 측정 버그다:**

| | 버그 | 고친 곳 |
|---|---|---|
| 1 | 바이트 단위 로드 | L8g |
| 2 | 의존성 체인 | L8g |
| 3 | **`volatile` 직렬화** | L8n |

고침(L8n): 포인터를 일반 `const` 로 두고, 로드가 지워지지 않게
 · 합을 호출자에게 돌려주어 찍고
 · `reps` **사이**에만 컴파일러 장벽 `__asm__ volatile("" ::: "memory")` 을 둔다.
   루프 **안**은 건드리지 않으므로 로드가 자유롭게 파이프라인된다.

판정 기준: **4 KiB 가 32 MiB 보다 뚜렷이 빠르면 캐시는 정상**이고, 남은
레버는 클럭(2.2×)과 스레드(4×)뿐이다. 여전히 평평하면 그때 코어 쪽
(DSU/코히런시)을 본다.

# 2026-11-07 밤 — L8n: `volatile` 가설은 **틀렸다**. 그런데 쓰기가 답을 줬다

`volatile` 을 떼도 **아무 차이가 없었다** — 여전히 3.50 평평하다.

```
읽기   4 KiB 3.50 · 16 KiB 3.54 · 32 KiB 3.44 · 256 KiB 3.05 · 32 MiB 2.95
쓰기  16 KiB **7.54** · 32 MiB **4.00**
```

## 쓰기가 캐시의 작동을 증명한다

**쓰기는 크기에 반응한다 (7.54 → 4.00, 1.9배).** 읽기는 반응하지 않는다.
두 영역(힙·블롭)의 PTE 는 동일하고(`MAIR 0xff`·`SH=3`) ALU IPC 는 1.99 다.

그리고 숫자가 맞는다:
```
쓰기 7.54 B/cyc = 64 B / 8.5 사이클 = **스토어당 1.06 사이클**   ← A55 정상
읽기 3.50 B/cyc = 64 B / 18.3 사이클 = **로드당 2.29 사이클**
```

A55 는 **인오더** 코어다. L1 로드 지연(약 3 사이클)을 숨기려면 컴파일러가
로드를 미리 띄워야 한다. 그런데 이 빌드는 **`-Os`**(`CONFIG_SIZE_OPTIMIZATIONS=y`)
다 — 크기 최적화는 그런 스케줄링을 하지 않는다. 스토어는 결과를 기다릴
필요가 없으므로 전속으로 돈다. 비대칭이 정확히 설명된다.

## 결론 — 캐시 문제는 **없다**

| 주장 | 상태 |
|---|---|
| "L1 이 안 먹는다" | **철회.** 쓰기가 크기에 반응한다 = 캐시는 작동한다 |
| "블롭 창의 매핑이 다르다" | **철회.** 두 영역의 PTE 가 완전히 같다 |
| "`volatile` 이 직렬화한다" | **철회.** 떼도 차이가 없었다 |
| 읽기 루프가 평평한 이유 | **`-Os` 에서 인오더 코어의 로드 지연** |

⚠ 이 벤치마크로는 읽기 **대역**을 잴 수 없다. 재는 것은 로드 지연이다.
  앞으로 이 숫자로 캐시를 논하지 않는다.

## 그런데 여기서 진짜 레버가 나왔다 — `-Os`

`CONFIG_SIZE_OPTIMIZATIONS=y` 가 **ggml 과 llama.cpp 전체**에 `-Os` 를 준다.
업스트림 llama.cpp 는 Release 에서 `-O3` 를 쓴다. 인오더 A55 에서 이 차이는
작지 않을 수 있다 — 위 측정에서 로드가 지연에 묶인 것이 그 증거다.

**다음 시험:** `CONFIG_SPEED_OPTIMIZATIONS=y`(`-O2`)로 L6c 를 다시 재고
토큰당 시간을 비교한다. 한 번에 한 변수만 바꾼다(`-O3` 는 그다음).

확인해 둘 것:
- **크기 여유** — L6c 는 RAM 97.41% 다. 아레나가 245,760 KB 이고 비-아레나가
  9,604 KB, 여유가 **6,780 KB** 다. 코드가 수백 KB 늘어도 들어간다
- **수치 동일성** — `-ffp-contract=off` 는 이미 고정돼 있다. 그래도 `-O2` 가
  평문 C 루프를 벡터화하면 누적 순서가 바뀔 수 있다. **12/12 토큰 일치가
  판정이다** — 깨지면 그 자체가 정보다

- Zephyr 트리에서 `SPEED_OPTIMIZATIONS` 를 `select`/`imply` 하는 곳 없음

**추측하지 않는다.** 경로를 못 찾았다고 적어 둔다. 실측은 분명하다 —

```
Current thread: 0x4045f2c0 (**main**)      x1 = 0xf0f0f0f0 (센티넬 패턴)
```
**넘친 것은 워커가 아니라 `main` 이었다.** `llama_init_from_model` 이 SMP +
4스레드에서 메인 스택을 더 쓴다(스레드풀 구성·그래프 예약).
`CONFIG_MAIN_STACK_SIZE` 를 64 KiB → **256 KiB** 로 올려 통과했다.

⚠ **진단 설정을 고침 후보와 함께 넣은 것이 결정적이었다.** 스택만 키웠다면
  또 `ELR=0` 을 보고 "스택이 아니다" 로 오진했을 것이다. 그리고 첫 시도의
  NULL 점프도 **같은 원인**이었다 — 센티넬이 없어 복귀 주소가 조용히 깨진 뒤
  15.6초에 엉뚱한 곳에서 터졌고, 센티넬을 켜니 9.0초에 정확한 지점에서 잡혔다.

⚠ `CONFIG_STACK_SENTINEL=y` 를 **켠 채로 둔다.** 끄면 다음 넘침이 또 NULL
  점프로 숨는다. 비용은 문맥 전환마다 몇 워드 검사이고 토큰당 421 ms 규모에서
  무의미하지만, **측정값에 섞여 있다는 점은 기록해 둔다.**

⚠ 워커 스택 128 KiB 는 **필요성이 증명되지 않았다** — 예방으로 둔 것이다.
  32 KiB 로 되돌려도 통과하는지는 재어 보지 않았다.

# 2026-11-08 — `-O3`: 토큰당 358 ms. 누적 **65.9배**

ggml·llama 소스와 앱 main **만** `-O3` 로 올렸다. 커널은 `-O2` 그대로다.

```
 1단계 382 · 2단계 370 · 3~12단계 358~359 ms
12/12 토큰 일치 · === L6c PASS (실패 0) ===
```

| | 토큰당 | 배수 |
|---|---|---|
| 아침 (1스레드 + UART 폭주) | 23,600 ms | — |
| UART 고침 | 1,423 ms | 16.6× |
| + 4스레드 | 421 ms | 3.38× |

## 로짓이 또 비트 단위로 같다

```
13.078794 · 14.422954 · 18.048634 · 14.399913 · 13.646799 · 16.927963
13.509903 · 13.674334 · 16.866117 · 11.101216 · 12.701114 · 14.994235
```

`-O2`·`-O3`·1스레드·4스레드 네 조합이 **모두 같은 로짓**이다. `-O3` 가
평문 C 루프를 벡터화할 수 있고 `-ffp-contract=off` 가 그것을 전부 막지는
못한다고 적어 두었는데, 실제로는 누적 순서가 바뀌지 않았다. **확인해야 했던
것이고, 확인됐다.**

## 구현

Zephyr Kconfig 에 `-O3` 선택지가 없다 (`Kconfig.zephyr:512-548` —
SIZE/`-Os` · SIZE_AGGRESSIVE/`-Oz` · SPEED/`-O2` · DEBUG/`-Og` · NONE/`-O0`).
그래서 파일 단위로 **뒤에 붙여** 덮는다 (gcc 는 마지막 `-O` 를 쓴다):

```
cmake/llm_ggml.cmake      set(LLM_GGML_OPT_LEVEL "" CACHE STRING ...)
                          llm_ggml_flags() 가 비어 있지 않으면 뒤에 붙인다
apps/llm_l6c/CMakeLists   set(LLM_GGML_OPT_LEVEL "-O3" CACHE STRING "" FORCE)
                          ⚠ include **전에** 세워야 한다 (CACHE 는 FORCE 없이
                            이미 있는 값을 이기지 못한다)
```

실제 명령줄로 확인했다:
```
-O2 -mcpu=cortex-a55 -mcpu=cortex-a55 -ffp-contract=off -O3
```
플래그 집계: **232 × `-O3`**(ggml + llama + main) · **182 × `-O2`**(커널).
의도대로 커널은 건드리지 않았다.

**되돌리기는 `CMakeLists.txt` 의 한 줄을 지우는 것이다.** 그러면 Kconfig 값
(`-O2`)으로 돌아간다.

대가: 코드 +508 KB (3,933,064 → 4,440,968 bytes), RAM 97.69% (여유 ~6.0 MB).
