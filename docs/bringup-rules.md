# 실기 왕복 규율 — 반복한 실수와 재발 방지

2026-11-03 ~ 11-05 의 bring-up 에서 **같은 종류의 실수를 반복**했다. 이 문서는
그 패턴을 규칙으로 바꾼 것이다. 작업을 시작할 때와 **실기 왕복 직전에** 읽는다.

실기 왕복 한 번의 비용은 사람이 SD 카드를 빼서 복사하고 다시 꽂고 전원을
넣는 것이다. 에이전트가 쓰는 토큰보다 그것이 비싸다. **왕복을 아끼는 것이
이 문서의 목적이다.**

---

## 굽기 전 체크리스트 (매번)

| | 질문 | 어기면 |
|---|---|---|
| 1 | **기준선을 잡았는가?** 마지막으로 동작이 확인된 바이너리를 먼저 굽는가 | 보드·카드·배선·전원·복사 절차가 전부 미검증 변수가 된다 |
| 2 | **이번 왕복의 변수는 1개인가?** 아니면 왜 아닌가 | 실패해도 아무것도 모른다 |
| 3 | **`.config` diff 를 봤는가?** `prj.conf` 가 아니라 생성된 `.config` 끼리 | `prj.conf` 2줄이 `.config` 70줄 차이였던 사례가 있다 |
| 4 | **성공하면 무엇이 가려지고, 실패하면 무엇이 가려지는가?** 둘 다 답할 수 있는가 | 답이 하나뿐이면 그 왕복은 절반만 쓴다 |
| 5 | **진단 코드가 피검체보다 단순한가?** init level 이 적법한가 | 진단이 피검체를 죽인다 (아래 사례 2건) |
| 6 | 보율·포트 이름·카드 장치명이 **지금** 상태와 맞는가 | 쓰레기를 데이터로 읽는다 |
| 7 | 진입점(`sdcard/boot.cmd` 의 `zentry`)이 **이 빌드**와 같은가 | `go` 가 엉뚱한 주소로 간다 |
| 7-b | **커밋한 뒤 재빌드했는가** — 스탬프된 해시가 HEAD 와 같은가 | 보드가 찍는 버전이 한 커밋 뒤처져, 그 해시를 찾으면 그 코드가 없다 |
| 8 | `sudo -v` 를 먼저 받았는가 · 복사 뒤 `mdir` 출력을 **봤는가** | 복사가 조용히 안 된 채 왕복을 쓴다 |
| 9 | **관측 채널이 지금 살아 있는가** — 이 왕복 직전에 그 채널로 무언가를 실제로 봤는가 | 채널이 죽은 것을 "피검체가 조용하다" 로 읽는다. 그 오독이 2026-11-06 에 왕복 6회를 태웠다 |

## 규칙 8가지 (각각 실제로 어겼던 것)

### 1. 기준선을 먼저 굽는다

실기 왕복을 시작할 때, 또는 **2회 연속 실패한 뒤**에는 다음 변경을 올리기 전에
**마지막으로 동작이 확인된 바이너리**를 굽는다. 그 한 번이 보드·SD 카드·배선·
전원·복사 절차·보율을 한꺼번에 검증한다.

> **어긴 사례.** `apps/usbuart` 가 동작하는 것을 알고 있었는데 굽지 않고 새
> `apps/moru` 에 Kconfig 를 20개 켜서 첫 왕복을 썼다. 실패 뒤 "보드가 죽었나,
> 카드가 문제인가, 배선인가"를 가릴 수 없어 **왕복 4회를 추측에 썼다.**

> **또 어긴 사례 (2026-11-06, OTA 2단계).** 수신이 느린 것을 고치면서
> ① hexdump 로그 끄기와 ② 폴링 스레드 → 콜백 전환을 **동시에** 했다. 결과가
> 0 바이트였는데, ② 때문인지 ① 전에도 0 이었는지 가릴 수 없었다 — 첫 시도에서
> `status` 를 확인하지 않아 기준선조차 없었다. **고칠 것이 둘 보이면 하나만
> 바꾼다.** 느린 것과 안 되는 것은 다른 증상이고, 둘을 한꺼번에 건드리면
> 어느 쪽을 고쳤는지 모른다.

### 2. 한 왕복에 변수 하나

"위험을 격리한다"를 계획서에 쓰고 실행에서 어겼다. 묶음으로 올려야 할 때는
**실패 시 어떻게 가를지**를 먼저 적는다.

계획에 적은 격리 전략과 실제로 구운 `.config` 가 같은지 **굽기 전에** 확인한다.

**사례 (2026-11-06, htop).** `CONFIG_THREAD_RUNTIME_STATS=y` 한 줄과 새 파일
372줄을 **한 번의 OTA 로** 올렸다. 부팅이 멈췄고, 어느 쪽 때문인지 모른다.
변수를 하나로 줄이는 것은 거의 공짜였다 — 코드를 남기고 Kconfig 만 빼면
된다. 다만 **그대로는 안 됐다**: `k_thread_runtime_stats_get()` 은 그 Kconfig
없이도 링크되고 0 을 돌려주지만(`kernel/thread.c:1161-1175`)
`k_thread_runtime_stats_t` 의 **멤버 자체가 조건부**라 `execution_cycles`
참조가 컴파일을 깬다. `#ifdef` 3줄이 필요했다. 그래도 **올리기 전에
확인했으면 왕복 하나로 갈렸다.**

(이 문단의 첫 판에는 "코드는 그대로 두고 뺄 수 있었다" 라고 썼는데
부정확했다 — 빌드가 실제로 깨지고서야 알았다.)

교훈: "이 둘을 쪼갤 수 있는가" 는 묶기로 결정한 **뒤**가 아니라 **전에**
묻는다. 쪼갤 수 있으면 쪼갠다.

### 3. `.config` 로 확인한다, `prj.conf` 로 확인하지 않는다

Kconfig 는 `select`·`default y if` 로 번진다. 두 빌드를 비교할 때는 생성된
`.config` 를 diff 한다.

```bash
diff <(sort /tmp/cfg-before) <(sort build/zephyr/.config) | grep '^[<>]'
```

> **어긴 사례.** `prj.conf` 2줄 차이가 `.config` 에서 70개 항목 차이였다.
> 비교 한 번이면 왕복 0회로 알 수 있었다.

### 4. 상관관계와 인과를 다른 말로 쓴다

**"원인을 찾았다" 를 쓰지 않는다.** 세 번 단정했고 세 번 틀렸다
(UART 인터럽트 설정 → `DW8250` busy-detect → `moru_stage.c`).

쓸 수 있는 말의 등급:

| 말 | 조건 |
|---|---|
| "유력하다 / 상관관계가 있다" | 실패한 판 전부에 있고 성공한 판에 없다 |
| "무죄가 입증됐다" | 성공한 판에 **켜져** 있다 |
| "유죄가 입증됐다" | 그 변수만 토글해 **두 방향 모두** 재현했다 (A→실패, A 제거→성공) |
| "기전이 설명됐다" | 코드·문서로 왜 그렇게 되는지 보인다 |

`CONFIG_INIT_STACKS` 는 지금 **"유죄 입증 + 기전 미설명"** 상태다. 이 구분을
문서에 그대로 남긴다 — 기전을 모르는 채 "해결했다"고 쓰면 다음 사람이 속는다.

### 5. 진단 코드는 피검체보다 단순해야 한다

초기 부팅 단계의 출력은 **`uart_poll_out` 또는 raw MMIO 만** 쓴다. `printk`·
`LOG_*`·`device_map()`·추가 스레드는 그 자체가 고장 원인이 된다. 새 진단 코드를
넣을 때 그것이 돌 **init level 의 제약**을 먼저 확인한다.

> **어긴 사례 2건.**
> - `moru_stage.c` 가 `SYS_INIT(..., PRE_KERNEL_1, 1)` 에서 `device_map()` 을
>   불렀다. 불법이다 — `z_mem_manage_init()`(`kernel/init.c:293`)이
>   `PRE_KERNEL_1`·`PRE_KERNEL_2` 보다 **뒤**에 돈다.
> - LED 하트비트 스레드 스택을 1024 로 두어 크래시했다.

### 6. "없음"은 증거가 아니다

긍정 확인만 증거로 쓴다.

| 쓰면 안 되는 추론 | 대신 확인할 것 |
|---|---|
| `diskutil list` 에 카드가 없다 → 복사 성공 | `mdir` 출력의 파일 크기 |
| 로그 파일에 문자열이 없다 → 출력이 없다 | 터미널 **화면**. `tio --log-file` 은 버퍼링이고 `--log-strip` 은 출력 불가 문자를 버린다 |
| 명령이 오류 없이 끝났다 → 다 됐다 | `sudo` 실패로 `&&` 사슬이 끊기면 조용히 안 된다. `sudo -v` 를 먼저 |
| 명령을 보냈다 → 실행됐다 | **응답을 읽어야 안다.** 포트를 열고 바로 쓰면 셸에 닿지 않는 경우가 있다 — `apply` 가 그렇게 사라져 "적용 실패"로 오진했다 |
| `write()` 가 반환했다 → 보냈다 | **커널 버퍼에 넣은 것일 뿐이다.** TTY/USB 는 큰 블록을 버퍼에 쌓고 내보내지 않을 수 있다 — 받는 쪽 수치로 확인한다 |
| **관측 채널이 조용하다 → 피검체가 조용하다** | **그 채널이 지금 살아 있는지 먼저 증명한다.** 2026-11-06: uart2 가 0 바이트인 것을 근거로 "U-Boot 조차 안 돈다 → 펌웨어는 용의자가 아니다" 라고 여러 번 말했다. 틀렸다 — 보드가 멀쩡히 도는(USB 열거되는) 상태에서도 uart2 는 0 바이트였다. **점퍼가 빠져 있었다.** A/B(롤백)가 정반대의 답을 줬다: 그 빌드가 범인이었다 |

> **어긴 사례 (2026-11-06, 포트 점유).** 셸 포트가 열리지 않자 "tio 를
> 닫으셨나" 만 두 번 물었다. `lsof` 로 보니 **`Xconsole.app` 이 5일째**
> 잡고 있었다. 점유자를 추측하지 말고 `lsof <포트>` 로 **실제로 누가
> 쥐고 있는지** 본다.

> **어긴 사례 (2026-11-06, 편집 스크립트).** 여러 패턴을 한 스크립트로
> 바꾸고 마지막에 한 번 저장했는데, 중간 `assert` 실패로 **아무것도
> 쓰이지 않았다.** 그런데 다른 블록은 저장에 성공했고, 나는 패턴 **하나만**
> `grep` 해 "전체가 실패했다" 고 단정했다. 같은 편집을 다시 적용해 중복이
> 생기고, 그것을 줄 단위로 지우다 **블록 시작 `{` 까지 삭제**해 빌드를
> 깨뜨렸다. → 패턴마다 **즉시 저장**하고, 확인은 **대상 전부를 센다.**

> **어긴 사례 (2026-11-06, OTA 전송).** 4096 바이트를 한 번에 `write` 하고
> "EAGAIN 0회로 다 보냈다"(3.1 MB/s)고 보고했지만 **보드는 0 바이트**였다.
> 64바이트씩 쪼개고 `tcdrain` 하니 96 %가 도착했다. 즉 보드는 처음부터
> 멀쩡했고 호스트 전송 방식이 문제였는데, **보드를 네 번 의심했다.**
> 송신 측 숫자는 수신 측 숫자로만 검증된다.

**관찰의 시각을 먼저 확인한다.** 같은 출력이 두 번 보이는 것은 재부팅 루프일
수도 있고 **전원을 두 번 넣은 것**일 수도 있다. 장치 목록이 비어 있는 것은
열거 실패일 수도 있고 **전원을 넣기 전에 본 것**일 수도 있다. 판정 전에
세 시각을 맞춰 본다 — ① 빌드 시각 ② 터미널 세션이 열린 시각
③ 사람이 전원을 넣은 시각.

> **어긴 사례 (2026-11-06, B1).** 터미널 로그에 마커가 두 번 보여
> "재부팅 루프" 로 단정했고, `ls /dev/cu.usbmodem*` 가 비어 있어 "열거 실패"
> 로 단정했다. 둘 다 틀렸다 — `tio` 는 15:34 에 열렸고 B1 빌드는 15:38 에
> 만들어졌다. 첫 마커는 **이전 빌드**의 것이고, `ls` 는 **전원 투입 전**에
> 실행했다. 시각 세 개를 맞춰 보면 즉시 알 수 있었다.

**보율이 틀린 구간의 쓰레기에서 문자열을 grep 하지 않는다.** 무작위 바이트에
찾는 글자가 섞여 거짓 양성·음성이 둘 다 난다. U-Boot 는 1.5 Mbps, Zephyr 는
115200 — 한 번에 둘 다 읽을 수 없다.

### 7. 기록을 먼저 읽는다

같은 증상이 나오면 추측하기 전에 기록을 grep 한다.

```bash
grep -n "증상 단어" docs/hardware-verified.md docs/bringup-rules.md README.md
```

> **어긴 사례.** 이 문서를 쓰는 중에도 `reset.S` 전제를 다시 의심했는데,
> `docs/hardware-verified.md` 가 이미 답하고 있었다 (동기 마커도 안 나오므로
> `PRE_KERNEL_2` 이전 확정). 1300줄 시간순 기록은 **검색해서** 쓴다.

### 8. 사용자의 관찰은 데이터다

사용자가 본 것을 내 모델로 설명해 치우지 않는다. 먼저 **그 관찰이 무엇을
재는지** 확인한다.

> **어긴 사례.** "상태가 더 심해졌다, 깨져서 보인다" 를 "악화가 아니다" 로
> 넘겼다. 실제로는 tio 보율이 U-Boot(1.5 Mbps)와 안 맞아 쓰레기를 보던
> 것이었다 — 즉 **그 관찰은 정확했고, 재던 대상이 달랐다.**

## 콘솔 원칙 — main 은 USB, 안 되면 UART 1개 (2026-11-06 사용자 확정)

평상시 콘솔·셸은 **USB CDC-ACM**. 안 되면 **UART 1개**로 들여다본다.
11-05 의 "둘 다 UART2" 를 뒤집는 결정이다 — USB 열거가 안정되고, USB 가
안 보일 때 원인을 가릴 관측 수단이 생겼기 때문이다.

그 관측 수단이 규칙 5("진단 코드는 피검체보다 단순")의 실제 적용이다:
`moru_mark.c` 가 `chosen` 을 따르지 않고 **uart2 에 직접** 동기 마커를
찍는다. USB 가 완전히 무음이어도 UART 어댑터만 꽂으면 커널이 어디까지
갔는지 보인다. 카드를 진단 빌드로 바꾸기 **전에** 이것을 먼저 본다.

빌드 두 가지와 가르는 순서는 `README.md` §콘솔 원칙과
`apps/moru/prj.conf` 맨 끝.

## 역할 경계 (전역 지침의 이 저장소 적용)

- **보드에 올리는 것은 사람이 한다.** 에이전트는 컴파일·복사 명령 준비·안내까지.
  `~/.claude/hooks/block-agent-flash.sh` 가 서브에이전트의 flash 류를 막는다.

- advisor(Fable)는 ① 계획 확정 직전 ② 같은 오류 반복·막혔을 때 ③ 완료 선언 직전.

## 사례 — **관측 경로가 QEMU 와 실기에서 달랐다** (2026-11-07)

사다리 L5b 를 실기에 처음 올렸는데 **완전히 조용했다.** UART2 에 한 글자도
나오지 않았다. 같은 코드가 QEMU 에서는 35줄을 찍는다.

규칙 6("관측 채널이 조용하다 → 피검체가 조용하다")을 적용해 채널을 먼저
의심했고, **같은 tio 세션으로 moru 출력이 보였으므로 채널은 정상**이었다.
그러면 피검체가 조용한 것인데, 원인은 피검체의 고장이 아니라 **관측 경로의
차이**였다:

```
보드 defconfig:  CONFIG_LOG=y                 (dwc3 드라이버 로깅용)
  → 따라오는 기본값:  CONFIG_LOG_PRINTK=y     printk 를 로그 시스템으로 우회
                      CONFIG_LOG_MODE_DEFERRED=y
                      CONFIG_LOG_BUFFER_SIZE=1024              1 KB
                      CONFIG_LOG_PROCESS_THREAD_SLEEP_MS=1000  1초씩 잠
                      CONFIG_MAIN_THREAD_PRIORITY=0            main 이 선점
QEMU 보드:       CONFIG_LOG 이 **꺼져 있다** → printk 가 직접 나간다
```

사다리 앱은 80자 수십 줄을 `main` 에서 쏟는다. 로그 스레드는 우선순위가
낮아 `main` 이 도는 동안 돌지 못하고, 1 KB 버퍼는 `LOG_MODE_OVERFLOW` 로
**오래된 것부터 버려진다.**

**고친 방법:** 사다리 앱 전부에 `CONFIG_LOG_PRINTK=n` 을 넣었다. `CONFIG_LOG`
자체를 끄지 않는다 — 드라이버 로깅은 그대로 두고 `printk` 만 콘솔로 직접
(동기) 보낸다.

### 규칙으로 남길 것

**"QEMU 에서 통과했다" 는 관측 경로까지 같다는 뜻이 아니다.**
보드 `defconfig` 가 앱에 Kconfig 를 주입하므로, 같은 앱이 두 보드에서
**다른 출력 경로**를 갖는다. 실기 첫 투입 전에 두 빌드의
`.config` 를 적어도 콘솔·로그 항목만큼은 비교한다:

```bash
diff <(grep -E '^CONFIG_(LOG|CONSOLE|PRINTK|SERIAL|UART)' A/zephyr/.config | sort) \
     <(grep -E '^CONFIG_(LOG|CONSOLE|PRINTK|SERIAL|UART)' B/zephyr/.config | sort)
```
